Dynamic nearby-events lookup at plan generationBacklogMAt plan generation time, perform a broad city-wide search for events on the occurrence date that could affect driving, parking, or transit — not just stadium sports (Acrisure Stadium, PNC Park) but any major event: concerts, conventions, circuses, festivals. Use Claude with web search tools or a general events API; a sports-only API is insufficient. Result populates a gameDayWarning in the plan: "Steelers home game at 1pm — North Shore parking severely constrained. Use T." or "No major events found nearby — normal Friday traffic expected." Mirrors the weather sourcing pattern: fetch → cache by occurrence+date → include in plan content.

Data layering rules (established 2026-08-30):
  • CityBound (PlatformCore) = stable base layer. City transit options, neighborhoods, general parking patterns, local tips — true regardless of the event date. ForumJourney reads this data; it never writes to or overwrites it.
  • ForumJourney dynamic layer = date-specific overlay. Events happening that day, weather, game-day warnings — fetched per occurrence at plan generation time and rendered on top of the CityBound base. Where there is a conflict (e.g. CityBound says "parking is straightforward" but the dynamic lookup finds a game and a circus), ForumJourney's date-aware advisory takes precedence in the plan output.
  • Venue guide data must never reference a specific event date. Guide docs are reused across all events at that venue. Any date-specific advisory belongs in the dynamic lookup, not baked into the venue record.
  • Search scope must be city-wide, not venue-adjacent. Pittsburgh (and cities like it) have traffic systems where an event anywhere downtown can ripple to the North Shore. The lookup question is: "what's happening in this city on this date that could affect driving and parking?" — not just "is there a game at the nearby stadium?"
Social intelligence sourcing for event format + logisticsBacklogMCommunity sources (Reddit, event review sites, partner website) can usefully inform event session structure, format details, and logistics — things the partner hasn't explicitly provided. Rule established 2026-08-30: (1) factual format data (session count, format type, agenda flow) can be ingested and stored on the event record; (2) editorial opinion (speaker quality complaints, crowd mix grievances) must never surface in attendee-facing plan content — ForumJourney is a partner platform, not a review site; (3) sourced data should be flagged with its origin so operators can verify before it affects production plans. At scale: operator reviews AI-proposed session structure from web research before it is committed to the event record.
Plan auto-purge on occurrence mutationBacklogSWhen occurrence date, venue, or time is changed via any operator or admin path (not just the inbound webhook), existing plan docs for that occurrence should be deleted so the next page load generates fresh content. Currently plans are only marked stale via the webhook change-detection flow — direct Firestore or script edits leave stale plans in place with baked-in old values (e.g. wrong date in AI-generated travel advice). Fix: call markPlansStaleForOccurrence (or delete docs outright) on any occurrence update path.

19. Data Collection Framework

~30% done
Extensible framework for collecting location-specific factual data, normalizing it into typed fact models, and preserving source provenance. Spec: ForumJourney_Data_Collection_Framework_Requirements_v0.1.docx. Organized in three layers: Collect (adapters, normalizers, categories) → Surface (wire facts into plans and portals) → Manage (operator controls). Phases 2–6 shipped 2026-09-05. Critical gap: the Collect layer is functional but the Surface layer is entirely unbuilt — normalizedFacts are written to Firestore but nothing reads them. The discoveries[] field in PlanContent is defined but never populated. Parking (Phase 5) is the only category with a complete adapter + normalizer; 8 of 9 categories have no adapter yet.
