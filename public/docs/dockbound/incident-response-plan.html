Personal Data Breach Response Plan

Entity: PandA Ventures, LLC (DockBound) Owner: Amy Abraham, Co-founder Version: 1.0 — Draft Date: September 2026 Covers: GDPR Art. 33–34 · UK GDPR · CCPA breach notification
72-Hour Clock The moment a breach is confirmed (or reasonably suspected), the 72-hour supervisory authority notification window begins under GDPR Art. 33. Do not wait for full investigation to complete before notifying. An initial notification can be supplemented.

§1 · Purpose and Scope

This plan defines how PandA Ventures, LLC ("DockBound") detects, assesses, contains, and reports personal data breaches. It applies to all systems that process personal data on behalf of DockBound: the DockBound Firebase project (Auth, Firestore, Cloud Functions), Stripe, SendGrid, Twilio, and any sub-processor listed in the Sub-Processor Register.

A personal data breach is any security incident that leads to the accidental or unlawful destruction, loss, alteration, unauthorised disclosure of, or access to, personal data (GDPR Art. 4(12)). This includes:

  • Unauthorised access to Firestore collections containing user, advisor, or traveler data
  • Accidental exposure of Firebase service account keys or API keys
  • Mass-deletion of user data (whether accidental or malicious)
  • Disclosure of traveler itinerary data to the wrong advisor or third party
  • SendGrid/Twilio mis-routing of personal communications
  • Stripe dispute data or payment details accessed without authorisation
  • Compromised admin account with access to the DSR/Privacy admin page

§2 · Severity Classification

Severity Definition Examples Response Time
P1 Critical Large-scale or high-risk breach; rights and freedoms of data subjects at serious risk Firestore database exported without auth; Firebase service account key leaked publicly; admin account compromised; bulk user PII exposed Contain within 4 hours; authority notification within 72 hours
P2 High Limited scope breach or disclosure; elevated risk but contained Single advisor's roster data visible to wrong advisor; Stripe customer record accessed by unauthorised party; SendGrid API key exposed in logs Contain within 24 hours; assess for authority notification within 48 hours
P3 Moderate Limited personal data affected; low risk to data subjects; confidentiality breach without likely harm Email address leaked in error log (non-public); single mistaken email send to wrong traveler; accidental exposure of non-sensitive field Contain within 72 hours; document internally; no authority notification unless risk escalates
P4 Low No personal data exposed; near-miss or availability incident only Firestore document temporarily unavailable; CF timeout with no data loss; internal audit log entry duplicated Document and review; no notification required

§4 · Response Procedure

Phase 1 — Detect and Assess (Target: within 2 hours of discovery)

  • 1
    Declare incident

    The person discovering the potential breach sends an email to amy@dockbound.app with subject line: [BREACH] [date] [brief description]. If Amy is the discoverer, she self-declares and begins the log.

  • 2
    Open incident log

    Create a dated entry in the Incident Register (see §8). Record: discovery timestamp, reporter, initial description, affected systems, estimated data subjects affected.

  • 3
    Classify severity

    Using the P1–P4 grid in §2, assign initial severity. When in doubt, assign the higher severity — it can be downgraded after investigation.

  • 4
    Confirm whether personal data is involved

    If the incident affects only non-personal data (port guides, DOCK scores, ship data), it is NOT a personal data breach under GDPR. Close as P4 and document the assessment.

Phase 2 — Contain (Target: within 4–72 hours depending on severity)

  • 5
    Revoke compromised credentials

    Firebase service account keys → Google Cloud Console → IAM & Admin → Service Accounts → delete key.
    API keys → /admin/api-keys → Revoke.
    SendGrid API key → SendGrid Dashboard → Settings → API Keys → Revoke.
    Firebase Secret Manager secrets → rotate via firebase functions:secrets:set SECRET_NAME.

  • 6
    Suspend affected accounts (if applicable)

    If a compromised admin account is suspected: Firebase Console → Authentication → find user → Disable account.
    If an advisor account is compromised: /admin/advisors/:uid → Suspend.

  • 7
    Restore Firestore rules if misconfigured

    If a Firestore rules misconfiguration caused the breach: immediately redeploy corrected rules via firebase deploy --only firestore:rules --project [project].

  • 8
    Preserve evidence

    Before rolling back or deleting anything: export relevant Firestore documents, capture Firebase Console audit logs, screenshot relevant Cloud Logging entries. Store in a dated folder in Google Drive.

  • 9
    Assess scope

    Determine: (a) which data categories were exposed; (b) how many data subjects are affected; (c) which countries they are in (EU/UK/US); (d) whether the breach is ongoing or contained.

Phase 3 — Notify (within 72 hours of confirmed breach for P1/P2)

  • 10
    Determine notification obligations

    Notify the supervisory authority if the breach is likely to result in a risk to the rights and freedoms of natural persons (GDPR Art. 33). Notify affected data subjects if the risk is high (GDPR Art. 34). See decision tree below.

  • 11
    File supervisory authority notification

    P1 and most P2 breaches require notification. Use the template in §5. Submit via the lead supervisory authority's online portal (see §6 for authority contacts). Deadline: 72 hours from when the breach was confirmed (or from when it was first suspected if confirmation is pending). A partial notification followed by a supplement is acceptable under Art. 33(4).

  • 12
    Notify affected data subjects (if high risk)

    If the breach is likely to result in high risk to individuals (e.g., financial harm, identity theft, safety risk), notify them directly without undue delay. Use the template in §5. Send via the email address on their DockBound account. If email is unavailable, use a prominent in-app notice or public communication.

  • 13
    Notify sub-processor if applicable

    If the breach originated with a sub-processor (Stripe, SendGrid, etc.), the sub-processor is responsible for notifying DockBound under their DPA. DockBound then assesses its own Art. 33 obligations. If DockBound caused a breach that exposed sub-processor-held data, notify the sub-processor immediately.

Phase 4 — Remediate and Review

  • 14
    Root cause analysis

    Within 7 days of containment: document root cause (misconfiguration, credential compromise, code defect, process failure). Record in the incident log.

  • 15
    Corrective action

    Implement fixes. Common actions: patch Firestore rules, rotate secrets, add input validation, update CSP, add monitoring alert, revise admin access controls.

  • 16
    Supplement supervisory authority notification if needed

    If the initial notification was partial, file a supplement via the same portal with full details once the investigation is complete (Art. 33(4)).

  • 17
    Close incident and update register

    Mark the incident closed in the Incident Register with: root cause, corrective actions taken, notifications filed, date closed.

§5 · Notification Decision Tree

QuestionYesNo
Is personal data involved? Continue assessment Not a GDPR breach — document as P4 security event and close
Is the breach unlikely to result in any risk to individuals? (e.g., encrypted data, already public info, no harm possible) No authority notification required — document internally in register per Art. 33(5) Continue assessment
Is the breach likely to result in some risk to individuals? Notify supervisory authority within 72 hours (Art. 33) —
Is the breach likely to result in high risk to individuals? (financial harm, discrimination, identity theft, physical harm, significant social/economic consequence) Also notify affected data subjects directly and without undue delay (Art. 34) No subject notification required; authority notification only
Does notification to subjects create disproportionate effort? (e.g., subjects cannot be identified) Use public communication or prominent in-app notice instead of individual notification Send individual notification

§10 · Prevention Controls in Place

DockBound has implemented the following technical measures to reduce breach risk:

  • Firestore security rules enforce role-based read/write; role, agencyId, privacyFlags fields blocked from client self-write
  • All Cloud Functions require Firebase ID token authentication; admin CFs additionally verify admin / super-admin role
  • Secrets (Stripe, SendGrid, Twilio, Travefy) stored in Firebase Secret Manager — not in code or environment variables
  • API key validation logs hash-mismatches and revoked key attempts to logs/ audit collection
  • Stripe webhook verifies stripe-signature header; failures logged to audit trail
  • GDPR erasure log written to gdpr_erasure_log/ with SHA-256 email hash — audit trail cannot be client-deleted
  • Automated retention enforcement CF (gdprRetentionEnforcement) deletes logs per retention schedule on the 1st of each month
  • GitHub secret scanning enabled — commits with credentials trigger email alerts
  • gdpr_erasure_log collection locked to CF write + admin read only via Firestore rules
