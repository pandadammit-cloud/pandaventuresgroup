Consumer & User Data

R-01 Account Identity & Authentication Controller
Data categoriesEmail address, display name, Firebase Auth UID, role, account creation/update timestamps
Data subjectsAll registered users (travelers, advisors, agency hosts, admins)
PurposeAuthentication, product access control, account management, role-based feature gating
Lawful basisContract — necessary to provide the service the user signed up for
Firestore locationusers/{uid} · Firebase Authentication (managed by Google)
RecipientsGoogle Cloud (Firebase Auth, Firestore) — see sub-processor list
RetentionDuration of account + 30 days post-deletion (to allow recovery). Firebase Auth record deleted on account erasure.
Transfer mechanismGoogle Cloud SCCs (US → EU/UK transfer coverage)
NotesRole field (role) and linked IDs (agentId, agencyId) are written only by Cloud Functions via Admin SDK — not writable by the client.
R-02 Subscription & Billing Data Controller
Data categoriesStripe customer ID, subscription status, plan type, trial end date, payment method type (card brand/last 4 — tokenised, never full PAN). Stripe stores card details — DockBound stores only the reference.
Data subjectsAdvisors (Compass/Chartroom/Helm) and travelers with paid access
PurposePayment processing, subscription management, access gating
Lawful basisContract — necessary to process payment and deliver the paid tier of service
Firestore locationusers/{uid} (plan status + Stripe customer ID only) · Full payment data held by Stripe
RecipientsStripe (payment processor) — see sub-processor list. Stripe handles card data under PCI-DSS.
RetentionStripe retains billing records for 7 years (tax/legal). DockBound's Firestore reference retained for duration of account + 30 days. Stripe customer record anonymised on account deletion (retain minimum for tax compliance per Stripe's DPA).
Transfer mechanismStripe SCCs / US-EU adequacy
NotesFull payment card data is never stored in Firestore. Stripe Radar fraud signals may retain limited transaction metadata — confirm retention period with Stripe DPA.
R-03 Traveler Self-Registration (post-login) Controller
Data categoriesName, email, phone (optional), SMS consent flag, cruise instances linked to account
Data subjectsTravelers who created their own DockBound account (distinct from advisor-uploaded roster entries)
PurposeDelivering personalised cruise/port content, traveler–advisor communications, SMS alert opt-in
Lawful basisContract (core account/content delivery). Consent (SMS — explicit opt-in required; never pre-selected).
Firestore locationusers/{uid} · agentRoster/{rosterId} (linked entry, set on invite acceptance)
RecipientsGoogle Cloud (Firestore). Twilio (SMS only, if consented). Advisor linked to this traveler.
RetentionTBD — active account duration + 30 days post-deletion. SMS consent log retained for 3 years (regulatory compliance).
Transfer mechanismGoogle Cloud SCCs. Twilio SCCs (if SMS enabled).
NotesSMS consent (smsConsent) is stored on the roster entry and must be explicitly set by the traveler — never defaulted to true. Erasure of this record must also trigger erasure of the corresponding pre-login roster entry (R-04) if one exists.

Advisor / B2B Data

R-04 Advisor-Uploaded Client Roster (pre-login / processor role) Processor
Data categoriesTraveler name, email, phone (optional), reference ID (optional), cruise + sail date, Travefy trip links, archive status
Data subjectsTravelers entered or imported by an advisor before the traveler has created their own DockBound account
PurposeEnabling advisors to manage client itineraries and send port guide communications on behalf of clients. DockBound processes this data on the advisor's (controller's) instruction.
Lawful basisProcessor role — the advisor (controller) is responsible for their lawful basis. DockBound's contract with the advisor must include a DPA clause covering this processing. DPA clause not yet in advisor ToS — pending
Firestore locationagentRoster/{rosterId}
RecipientsGoogle Cloud (Firestore). SendGrid (if advisor sends a port guide email to this traveler). Twilio (if SMS consent obtained and advisor sends SMS).
RetentionTBD — retained while advisor account is active + 90 days post-advisor-account-deletion. Archived entries (soft-deleted) retained for same period. Traveler erasure request triggers deletion of this entry in addition to R-03.
Transfer mechanismGoogle Cloud SCCs. SendGrid DPA. Twilio SCCs.
NotesThis is a processor-role record. The determination is accepted as a working position pending counsel confirmation. Advisor and agency terms of service must be updated to include a data processing clause before DockBound can formally act as processor for this data.
R-05 Advisor Profile & Settings Controller
Data categoriesContact name, agency name, email, advisor type, plan/subscription, Stripe customer ID, alert settings (email address + phone for notifications), Travefy connection metadata (userId, publicKey, connected timestamp — no access token client-side)
Data subjectsTravel advisors (Compass / Chartroom / Helm tiers)
PurposeService delivery, billing, alert notifications, Travefy integration management, agency hierarchy
Lawful basisContract
Firestore locationagents/{uid} · nodes/{nodeId} (hierarchy) · agencies/{agencyId} (agency record)
RecipientsGoogle Cloud (Firestore). Stripe (billing). SendGrid (alert emails). Twilio (SMS alerts if enabled). Travefy (integration — email used as lookup key only).
RetentionTBD — active account + 30 days post-deletion. Stripe billing records 7 years.
Transfer mechanismGoogle Cloud SCCs. Stripe SCCs. SendGrid DPA. Twilio SCCs. Travefy DPA.
NotesTravefy access token is stored server-side only in Firebase Secret Manager and Cloud Functions environment — never in Firestore or exposed to the client.

Firestore locationagentCommunications/{agentId}_{rosterId} (thread metadata) · agentCommunications/{id}/messages (subcollection)
RecipientsGoogle Cloud (Firestore). SendGrid (email delivery of port guide sends, logged in guide_send_log).
RetentionTBD — suggest 3 years from last message. guide_send_log suggest 2 years.

R-07 SMS Alerts & Interactions (Twilio) Controller
Data categoriesPhone numbers, inbound/outbound message content, consent flags (smsConsent, smsPendingConfirmation), consent timestamp
Data subjectsTravelers who have opted in to SMS alerts; advisors who enable SMS notification preference
PurposePort change alerts and advisor–traveler SMS communications (pending Twilio A2P approval)
Lawful basisConsent — explicit opt-in required. SMS consent must never be pre-selected. TCPA compliance required for US numbers.
Firestore locationagentRoster/{rosterId}.traveler.smsConsent · agents/{uid}.alertSettings.sms · Message content held by Twilio
RecipientsTwilio (SMS delivery and message log retention)
RetentionConsent log: 3 years (regulatory). Twilio message logs: align with Twilio DPA retention terms. Confirm with Twilio DPA
Transfer mechanismTwilio SCCs / DPA
NotesTwilio A2P 10DLC campaign pending approval as of 2026-09-17. SMS features gated until approved. Inbound JOIN keyword (ADVISOR_INVITE_KEYWORD) generates an invite code — no personal data stored beyond phone number.
R-08 Travefy Integration Controller
Data categoriesAdvisor's Travefy user ID, public API key, connected-at timestamp, optional email override. No traveler personal data transits the Travefy API.
Data subjectsAdvisors who connect their Travefy account
PurposeLinking the advisor's DockBound account to their Travefy account to enable DockBound to push port guide TripEvents into Travefy itineraries. Content pushed is port guide / DOCK score data (non-personal).
Lawful basisContract — the advisor initiates the connection and it is core to the Travefy integration feature
Firestore locationagents/{uid}.travefyConnection (userId, publicKey, connectedAt) · travefyEnrichments/{agentUid}_{tripId}_{portCode} (enrichment history — no personal data, only port codes and timestamps)
RecipientsTravefy (API calls to push TripEvents). Google Cloud (Firestore).
RetentionConnection metadata: active account duration + 30 days. Enrichment history: TBD — suggest 2 years.
Transfer mechanismTravefy DPA. Google Cloud SCCs.
NotesTravefy access token (secret) is stored in Firebase Secret Manager and used only within Cloud Functions — never in Firestore or the client. The advisor's email is used as a Travefy API lookup key but is already held by DockBound as R-05. No additional personal data is collected via Travefy.

Security Measures (Art. 32 — Applied to All Records Above)

Encryption at rest and in transit All personal data in Firestore and Firebase Auth is encrypted at rest using AES-256 by Google Cloud by default. All data in transit is encrypted via TLS 1.2+. Google Cloud's default encryption satisfies Art. 32(1)(a) for the data categories described in these records.
MeasureImplementationSatisfies
Encryption at restGoogle Cloud AES-256 default encryption on all Firestore collections and Firebase AuthArt. 32(1)(a)
Encryption in transitTLS enforced on all Firebase SDK connections and Cloud Function HTTP endpointsArt. 32(1)(a)
Access controlFirestore Security Rules enforce role-based read/write; privileged fields (role, agencyId, privacyFlags) blocked from client self-write. Admin Cloud Functions verify ID token + role.Art. 32(1)(b)
Secrets managementStripe, SendGrid, Twilio, Travefy credentials in Firebase Secret Manager — not in source code or frontend-accessible configArt. 32(1)(b)
Retention enforcementgdprRetentionEnforcement CF deletes records past retention period on the 1st of each monthArt. 5(1)(e)
Audit loggingAll admin actions on personal data written to logs/ with 7-year retentionArt. 32(1)(d)
Breach detectionAPI key hash-mismatch and Stripe signature failures logged; full procedure in docs/incident-response-plan.htmlArt. 32(1)(d) + Art. 33

Out of Scope (Confirmed)

The following are confirmed not personal data and are outside the scope of these records. Port guides and section content (locations/{portCode}/sections/*), DOCK scores (dock_scores_baseline, dock_scores_adjusted), port schedules (port_schedule), weather data, State Department travel advisories, cruise itinerary data (ship names, ports, dates — not linked to individuals), and Apify-scraped cruise data. None of these describe identifiable natural persons.
