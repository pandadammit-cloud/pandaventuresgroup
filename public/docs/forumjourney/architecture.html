1. System Overview

ForumJourney is an API-first event readiness platform. Partners (event organizers) integrate via REST API. Attendees receive personalized pre-event plans via a public URL — no login required. Multi-role portals for organizers, venue staff, and speakers launched August 2026.

ComponentProject IDNotes
Development environmenteventbound-devDefault alias in .firebaserc
Production environmenteventbound-prodDeploy with firebase deploy --project production
Branding note: External brand is ForumJourney (rebranded August 2026). Internal project ID remains eventbound-dev — Firebase project IDs are immutable. Outbound webhook payloads and UI assets use the ForumJourney name. Keep internal code and IDs as-is unless a file explicitly uses the ForumJourney brand.
PlatformCore retired 2026-08-31. The external guide warehouse is no longer active. Venue guide data lives in venues/{id}.guide and city guide data in cities/{id}.guide, edited via the venue portal or admin tooling. The PLATFORMCORE_API_KEY secret is still declared in index.ts but PlatformCore calls have been removed from all active code paths.

3. Cloud Functions

Two exported functions, Node 22 runtime, Gen 2, region us-central1:

api

onRequest wrapping an Express app. Handles all HTTP traffic.

  • Secrets: PLATFORMCORE_API_KEY (declared; PlatformCore retired), ANTHROPIC_API_KEY, OPENWEATHERMAP_API_KEY
  • CORS restricted to explicit ALLOWED_ORIGINS array (8 origins: Firebase Hosting dev/prod, forumjourney.app, localhost). Configured on onRequest options — not Express middleware.

onChangeCreated

onDocumentCreated Firestore trigger on changes/{changeId}. Fires webhook delivery when a change document is created.

  • Retries enabled
  • Secret: ANTHROPIC_API_KEY

5. Domain Flows

5.1 Plan Generation

  • Triggered by POST /v1/plans or GET /public/plan/:occurrenceId
  • generatePlan() in src/domain/plan/generator.ts fetches Occurrence, Event, Venue, City
  • Fetches weather and parking facts in parallel (Promise.all): weather uses stage-aware cache; parking facts query normalizedFacts with category='parking', limit 10, falls back to [] on error
  • assembleContent() in src/domain/plan/content.ts builds stage-appropriate PlanContent
  • Plan stage auto-detected from days until event: registration (>30d) → plan (8–30d) → prepare (1–7d) → attend (day-of or past). Per-partner stage thresholds override global defaults.
  • Plans upserted with deterministic doc ID: {occurrenceId}_{attendeeId|anonymous}_{stage}
  • Venue guide (venues/{id}.guide) and city guide (cities/{id}.guide) read directly from Firestore and overlaid on the public plan response
  • Parking normalizedFacts surface in content.discoveries[] when present (category=parking)

5.2 Change Detection & Webhooks (Inbound)

  • Partners POST to POST /v1/webhooks/partner-events
  • HMAC-SHA256 signature verified on raw body bytes (before JSON parse) via X-ForumJourney-Signature header
  • Timestamp replay check (±5 minutes); idempotency check against processedWebhooks collection
  • detectMaterialChanges() diffs stored vs incoming fields; creates Change documents for material changes
  • Affected plans marked stale; processedWebhooks record written
  • organizerVerified and verifiedAt stripped from inbound partner payloads — system-set only

5.3 Outbound Webhook Delivery

  • Firestore trigger onChangeCreated fires on each new changes document
  • deliverWebhook() in src/domain/webhooks/deliver.ts signs payload with HMAC-SHA256, POSTs to partner webhook URL
  • Payload type: forumjourney.plan.changed
  • Retries up to 3 times; marks dead_letter on exhaustion
  • Operator can manually retry via POST /operator/changes/:changeId/retry
  • Payload includes notificationContent with factual + conversational notification variants

5.4 Notification Content Generation

  • Factual variant: rule-based string from src/domain/notifications/factual.ts
  • Conversational variant: generated by Claude claude-haiku-4-5 via @anthropic-ai/sdk in src/domain/notifications/conversational.ts
  • Claude failure falls back to the factual message — conversational is never required

5.5 Data Collection Framework

The sourcing pipeline enriches occurrences with categorized local intelligence that surfaces in plan discoveries[] and venue guides.

  • Trigger: POST /v1/collection/run or admin-initiated per occurrence
  • Runner: src/sourcing/runner.ts — resolves the EventCollectionSpecification (creates one if absent), iterates enabled categories, creates CollectionJob per active source, invokes adapters
  • Adapters: implement SourceAdapter interface (src/sourcing/adapters/types.ts) — active: google_places_parking, googlePlaces, openStreetMap
  • Normalization: adapter raw payload → FactCandidate[] via category normalizers (src/sourcing/normalizers/parking.ts)
  • Storage: raw payload → rawSourceRecords; normalized facts → normalizedFacts
  • Geography: src/sourcing/geography.ts provides typed GeographicRule builders and Haversine-based pointInRule(). Default radii: parking 1.0 mi, transit 1.5 mi, dining 1.0 mi, activities 10.0 mi.
  • Credentials: adapter API keys resolved at runtime from GCP Secret Manager via src/lib/secrets.ts (resolveCredential()); falls back to env var if no credential ref
  • Admin UI: /operator/sources/* routes manage the sourceRegistry — propose, approve, reject, configure sources

5.6 Weather Sourcing

  • src/lib/weather.ts fetches from OpenWeatherMap (current conditions for attend, 5-day forecast for prepare) and overlays NWS active alerts
  • Stage-aware Firestore cache: 30 min for attend, 4 h for prepare (collection: weatherCache)
  • API key: OPENWEATHERMAP_API_KEY Firebase Secret
  • Returns null gracefully if coordinates or key absent; plan generator adds 'weather' to missingData

5.7 Join & Portal Auth

  • POST /public/join validates a join code against attendeeCode or venueCode on the occurrence
  • On match: checks seat limit, checks duplicate registration, creates or links a Firebase Auth user, sets custom claims (role, occurrenceId, firstName), creates attendee record, returns a custom token for immediate sign-in
  • Portal middleware (portalAuthMiddleware) validates any Firebase ID token and extracts uid, role, occurrenceId, venueId, partnerId into req.portalUser

6. Data Model

All Firestore collections deny client-side access. All writes go through the Admin SDK.

partners

Key: {partnerId}

API credentials (hashed key), webhook URL, inbound/outbound HMAC secrets, active flag, optional stageThresholds for per-partner plan stage day overrides.

cities

Key: {cityId}

Name, timezone, transit and weather overview. guide field: hand-curated city guide (replaces PlatformCore city guides).

venues

Key: {venueId}

Address, coordinates, entrances, accessibility, parking. guide field (VenueGuide type): getting-there options, in-the-know tips, arrival advice. Edited via PATCH /venue/data/:venueId.

events

Key: {partnerId}_{externalEventId}

Event details, admission policy, sessions, status. Partners scope all event data.

occurrences

Key: {occurrenceId}

Date, time, timezone, links to event + venue + city, status, attendeeCode, venueCode for join flows.

plans

Key: {occurrenceId}_{attendeeId|anonymous}_{stage}

Generated plan content, stage, stale flag, missingData list.

changes

Key: auto-ID

Material field changes detected from inbound webhooks. Each change document triggers outbound webhook delivery via Firestore trigger.

attendees

Key: {occurrenceId}_{uid}

Attendee email, firstName, role (attendee | venue), plan URL, notification preference.

feedback

Key: auto-ID

Rating (1–5), reason, plan reference.

overrides

Key: auto-ID

Manual field overrides with urgency and audit trail (author, reason, original value, new value).

processedWebhooks

Key: {idempotencyKey}

Deduplication log for inbound partner webhooks. Prevents reprocessing on retry. TTL field expiresAt set.

sourceRegistry

Key: {sourceId}

External data source config: adapter ID, category, credential ref, reliability, refresh profile. Managed via /operator/sources/* routes.

normalizedFacts

Key: auto-ID

Normalized, source-agnostic facts indexed by occurrenceId + category. Payload shape is category-specific (e.g., ParkingFactPayload). Queried by plan generator for parking discoveries.

rawSourceRecords

Key: auto-ID

Raw payloads from adapter fetch calls. Preserved for audit and re-normalization.

collectionJobs

Key: auto-ID

Job execution record: status (pending/running/completed/failed), attempts, raw record IDs, normalized fact IDs, geographic rule used.

collectionSpecifications

Key: auto-ID

Per-occurrence collection config: enabled categories, geographic overrides, collection window, status.

sourceChangeRequests

Key: auto-ID

Proposed source changes awaiting admin approval/rejection workflow.

sourceValidations

Key: auto-ID

Validation run records for data sources — health checks, reliability scoring.

weatherCache

Key: {occurrenceId}_{stage}

Cached weather fetch results. TTL: 30 min (attend) / 4 h (prepare). expiresAt field set for Firestore TTL.

venueNotes

Key: auto-ID

Conference notes written by venue staff, private to venue role. Indexed by occurrenceId + createdAt (composite index required).

speakerRequests

Key: auto-ID

Speaker special requests per occurrence. Indexed by occurrenceId + speakerUid + createdAt (composite index required).

speakerPresentations

Key: {occurrenceId}_{speakerUid}

Presentation URL (file upload stubbed — OD-19). One record per speaker per occurrence.

logs

Key: auto-ID

Interaction audit log — public plan views, portal logins, key user actions. Structured JSON entries.

leads

Key: auto-ID

Landing page lead submissions: name, email, organization, use case. Status field for CRM workflow (new → contacted → complete → archived). Visible in operator leads tab.

agenda

Key: {occurrenceId} (or session sub-document)

Live Firestore-backed session agenda. Managed via organizer dashboard CRUD. Replaces static session arrays.

8. Environment & Deployment

Commands

Functions (run from functions/):

npm run build # tsc compile to lib/ npm run build:watch # watch mode npm run test # vitest run — 132 tests, 16 files npm run test:watch # vitest watch npm run serve # build + start local emulators (functions + firestore)

Frontend (run from frontend/):

npm run dev # Vite dev server (hot reload) npm run build # tsc + vite build → dist/ npm run preview # preview production build

Firebase deployment (run from repo root):

firebase deploy # deploy everything firebase deploy --only hosting # frontend only firebase deploy --only functions # functions only firebase deploy --only firestore # rules + indexes only
Always build before deploying functions. Run cd functions && npm run build then cd .. && firebase deploy --only functions. Deploying without a fresh build causes "User code failed to load / Timeout after 10000" — the CLI analyzes compiled lib/ output, not TypeScript source.
