1. Access & Roles

Firebase Auth controls all portal access. A custom role claim must be set on the user's Firebase account. Role ranks determine what pages are accessible (higher number = more access).

RoleRankPortal AccessNotes
apiadmin100Operator Dashboard (full)PandA Ventures superuser; no partnerId required; cross-partner access
eventbound_operator60Operator DashboardLegacy alias — accepted for backward compatibility
operator40Operator DashboardScoped to a single partner via partnerId claim
organizer20Organizer DashboardEvent organizer; accesses agenda CRUD, attendees, requests
speaker15Speaker PortalPresentation management, special requests
venue12Venue PortalGuide data edits, conference notes (private)
attendee10Attendee Portal + EventsPickerPlan, agenda, personal notes, favorites

How to Set a Role

Use the Admin SDK script from the repo root. Do not set roles directly in the Firebase console — always use this script so occurrenceId and other required claims are set correctly.

NODE_PATH=functions/node_modules node scripts/set-claims.js

Or via the join flow: attendees and venue staff self-register using a join code. The POST /public/join endpoint creates the Firebase Auth account and sets claims automatically.

After setting custom claims, the user must sign out and sign back in for the new role to take effect. The ID token caches the old claims until it refreshes.

3. Operator Journeys

Journey A — New Partner Setup

  1. Create a partner document in Firestore (partners collection) with name, active: true, webhookUrl
  2. Generate an API key (random string) and compute its SHA-256 hash
  3. Store apiKeyHash in the partner document — never store the raw key
  4. Provide the partner with their raw API key and API documentation
  5. Coordinate with partner to set inboundWebhookSecret — store this in the partner's Firestore doc
  6. Set outboundWebhookSecret in the partner's Firestore doc (ForumJourney uses this to sign outbound webhooks)
  7. Optionally set stageThresholds: { plan: N, prepare: N } to override global plan stage day defaults

No UI for partner creation — done directly in Firestore console or via Admin SDK script. Admin-only by decision (OD closed).

Journey B — Set Up an Occurrence for Attendees

  1. Partner creates occurrence via POST /v1/occurrences with date, time, venue, city
  2. Generate attendee join code and set attendeeCode on the occurrence in Firestore
  3. Optionally set venueCode for venue staff access
  4. Distribute join code to attendees; they self-register at /join
  5. Create organizer account via scripts/set-claims.js with role: organizer + occurrenceId

Journey C — Generate a Plan

Via API:

POST /v1/plans { "occurrenceId": "disrupthr-pittsburgh-2026-oct21" }

Or navigate directly to the public plan URL: [domain]/plan/{occurrenceId} — ForumJourney generates the plan on first access if one doesn't exist.

Journey D — Handle an Event Change

  1. Partner POSTs an event update to POST /v1/webhooks/partner-events with X-ForumJourney-Signature header
  2. ForumJourney validates signature, timestamp (±5 min), and idempotency key
  3. Material changes are auto-detected; affected plans marked stale; outbound webhook fired to partner
  4. No manual operator action required unless webhook delivery fails

Journey E — Handle Dead-Letter Webhook Delivery

  1. In Operator Dashboard → Dead-Letter tab, find the failed change
  2. Inspect failure details (HTTP status, error message)
  3. Investigate the partner's webhook endpoint for availability issues
  4. Click "Retry" — calls POST /operator/changes/:changeId/retry
  5. Alternatively: update webhookStatus to 'pending' directly in Firestore — the Firestore trigger will re-fire

Journey F — Seed a New City

  1. Create a city document in Firestore (cities collection) with name, timezone, guide field
  2. Or run from repo root: node scripts/seed-new-cities.js with the city data file

Journey G — Trigger Data Collection for an Occurrence

  1. Via API: POST /v1/collection/run with occurrenceId and optional categories array
  2. Monitor job status via GET /v1/collection/jobs/list
  3. Normalized facts flow automatically into the next plan generation for that occurrence
  4. For new data sources: propose in Operator Dashboard → Sources tab; admin approves; source becomes active

Journey H — Manage Leads

  1. In Operator Dashboard → Leads tab, review new submissions
  2. Use the status dropdown to move leads through: new → contacted → complete / archived
  3. Note: leads are capped at 200 in the API response (pilot scale)

4. Data Management

Manual Overrides

Use overrides to correct event or venue field data without waiting for a partner update. Overrides include a full audit trail.

POST /v1/overrides { "targetType": "event", "targetId": "evt-001", "field": "admission.bagPolicy", "originalValue": "No bags", "newValue": "Small bags under 14\" allowed", "author": "ops@forumjourney.app", "reason": "Venue updated policy day-before", "urgency": "high" }

Venue Guide Editing

Venue staff can edit guide fields via their portal (PATCH /venue/data/:venueId). The guide lives at venues/{id}.guide in Firestore. Fields include getting-there options, in-the-know tips, arrival advice, accessibility notes. Changes take effect on the next plan fetch — no redeploy needed.

Source Registry

The sourceRegistry Firestore collection controls which external data sources are active and their configurations. Each document specifies adapter ID, category, credential ref, reliability, refresh profile. Managed via Operator Dashboard → Sources tab or directly in Firestore console.

Backlog Sync

The shared pandaventuresgroup backlog is seeded from scripts/seed-backlog.js. ForumJourney items use fj-* doc IDs. Run node scripts/seed-backlog.js --dry-run to preview changes before writing. Requires service account at C:\Users\Amy\secrets\pandaventuresgroup-service-account.json.

5. Security Operations

Rotate a Partner API Key

  1. Generate a new raw key (random secure string)
  2. Compute its SHA-256 hash:
    echo -n "RAWKEY" | sha256sum
  3. Update apiKeyHash in the Firestore partner document
  4. Provide the partner with the new raw key — the old key is immediately invalid

Rotate a Webhook Secret

Hard break: Rotating the inboundWebhookSecret immediately invalidates all requests signed with the old secret. Coordinate timing with the partner — there is no transition window. (Safe pre-pilot; post-pilot requires a dual-header window.)
  1. Agree on a rotation time with the partner
  2. Update inboundWebhookSecret in the Firestore partner document at the agreed time
  3. Partner updates their signing key at the same time
  4. The same process applies to outboundWebhookSecret

Replay Protection

Inbound webhooks are rejected if:

  • Timestamp in payload is more than 5 minutes old
  • Timestamp is more than 5 minutes in the future
  • Idempotency key already exists in the processedWebhooks collection

processedWebhooks records have a expiresAt TTL field set for Firestore automatic cleanup.
