1. Purpose & Scope

This document defines what the DockBound platform administration layer should be able to do — including capabilities that do not yet exist. It is meant to serve as a product roadmap for internal tooling and to make the gap between current state and ideal state explicit.

How to read this doc: Each section contains a mix of what is already built Built, what is partially built Partial, and what is missing Gap. The gap analysis in section 7 prioritizes everything missing into P1/P2/P3 tiers.

The admin role in DockBound has two distinct jobs: platform operations (keeping data pipelines running, content quality high, and accounts healthy) and business intelligence (understanding how the platform is being used, by whom, and how it is performing financially). This spec covers both.

4. Admin Journeys

Each journey below is an end-to-end admin task. Where steps are not yet possible due to missing tooling, a gap note is included.

Journey A — Rebuild / Regenerate a DOCKGuide

Trigger: A port guide has stale, missing, or incorrect content. Goal: Get it to publishable quality.
  1. Identify the gap — Open Content Health (/admin/content-health); filter to find the port with incomplete or stale sections. Or start from a user feedback report (Feedback Viewer) that flagged a specific port.
  2. Review existing content — Open the Port Guide Editor for the port; review each section to determine what is missing vs. just outdated.
  3. Generate missing sections — Use "Generate Port Content" to draft any empty or thin sections via OpenAI. Review the generated draft carefully — AI content should always be verified.
  4. Fact-check existing sections — Run "Fact-Check Content" on sections that have content but may be outdated. Review each flag and use "Apply Fact-Check Suggestion" to accept corrections.
  5. Manual edit — Open the Port Guide Editor and make any final edits — local knowledge, formatting, tone.
  6. Verify DockScore — Check DOCK Diagnostics for the port to confirm the score reflects the updated content correctly.
  7. Confirm live — Open a traveler-facing dashboard or preview for that port and confirm the updated content is visible.
⚠️ Gap: There is no "publish" workflow — all edits go live immediately on save. For a port receiving high traffic, this means potentially incomplete content is visible mid-edit. A draft/publish toggle would be useful (P2).
⚠️ V4 content gap: Port guides with schemaVersion: 4 support new cruise-intelligence fields (portAreaActivityDepth, returnComplexity, impactAction, majorExperienceTransferTime, returnDependencies) that power the "Port Day at a Glance" section visible to advisors and travelers. These V4 fields are not yet included in the AI content generation prompts — the Port Guide Editor must be used to set them manually until the prompts are updated.
✅ Built (QA Review): After generating content, the onSectionWriteQA trigger automatically validates each written section. The QA Review tab on Content Health surfaces all sections with issues. Admin should review any "Needs Review" dispositions and submit a reviewer decision before considering the guide publishable. Use "Download Fixture" to add a golden regression fixture from any approved section.

Journey B — Onboard a New Agency

Trigger: A host agency has agreed to join DockBound. Goal: Get the agency live and the host able to import their roster.
  1. Create the agency — Navigate to Agencies (/admin/agencies); click "Create Agency"; enter agency name, select the host user (must already have a DockBound account), and optionally add website and phone. Creating the agency also creates a corresponding org node in the Node system and writes nodeId to both the agency doc and the owner user doc — this is the canonical hierarchy record; do not add parentAgencyId or other hierarchy fields directly to the agency model.
  2. Verify host access — Confirm the host user's role was set to agencyhost and that they can see the Agency Hub at /agency-hub.
  3. Share referral code — The agency referral code is auto-generated on creation. Share it with the host so they can give it to advisors who sign up independently.
  4. Guide host through CSV import — Walk the host through importing their advisor roster at /agency-hub/import; confirm invite emails are sent. Each activated advisor gets a user node created under the agency's org node; removing an advisor deletes their user node.
  5. Monitor invite acceptance — The Agency Hub dashboard auto-detects advisor issues on each load — including inactivity after 14 days — and surfaces them as Attention Items. Check the attention items panel on the host's Agency Hub rather than the detail page alone.
  6. Verify advisor onboarding — Confirm at least one advisor has completed sign-up and appears as active on the roster.
⚠️ Gap: Step 5 still benefits from manually checking the agency detail page for counts. A "follow-up needed" flag for agencies with pending invites older than 7 days would complement the attention system (P2).

Journey C — Investigate an Advisor Account

Trigger: An advisor reports a problem — wrong tier, Travefy not syncing, roster not loading. Goal: Diagnose and resolve the issue.
  1. Look up the user — Currently requires going to Firebase Console → Authentication → search by email to find the UID. (No admin user-lookup UI exists yet.)
  2. Check role and tier — Query Firestore: users/{uid} for role, agents/{uid} for tier/slotsUsed/subscription status.
  3. Check Travefy connection — Look for agents/{uid}.travefyConnection in Firestore. If missing, the advisor has not connected their Travefy account.
  4. Resolve Travefy email mismatch — If the advisor used a different email in Travefy than in DockBound, use the Travefy override tool in Agent Tools (/admin/agents) to manually link by UID + Travefy email.
  5. Check roster — Query Firestore: agentRoster collection filtered by agentId. Count entries vs. tier cap.
  6. Resolve tier issue — If the advisor is on the wrong tier, update agents/{uid}.tier directly in Firestore. (No UI for this yet.)
  7. Trigger manual sync — If Travefy trips are not syncing, call syncTravefyTrips Cloud Function directly for the advisor's UID.
  8. Check communication threads — Query Firestore: agentCommunications collection filtered by agentId to see all threads and unread counts for the advisor. Review messages subcollection if a specific correspondence record is disputed.
⚠️ Gap: Steps 1, 2, 3, 5, 6, and 8 all require direct Firestore access — there is no admin UI for looking up and editing a specific advisor's account. An Advisor Detail page at /admin/advisors/:uid is the highest-priority admin gap (P1). Note: twilioInboundWebhook is built and handles both keyword SMS (JOIN → invite code reply) and traveler thread replies. Outbound SMS via sendTravelerSms requires Twilio secrets (TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_PHONE_NUMBER) and the inbound webhook registered in the Twilio Console — both require Twilio account activation before production use.

Journey D — Grant Comped / Free DOCKGuide Access

Trigger: A traveler should receive free access — a partnership, a comp request, a customer service issue. Goal: Give them full DOCKGuide access without a Stripe payment.
  1. Locate or create the user — Find the traveler's account by email in Firebase Auth.
  2. Identify the cruise — Determine the correct cruise ID from the cruises Firestore collection or from the traveler.
  3. Create a comp order — Manually create a document in the orders Firestore collection with status free or completed, the user's UID, and the cruise ID.
  4. Set purchase flag — Update users/{uid}.hasPurchasedCompass: true and add the cruise instance to cruiseInstances.
  5. Verify access — Have the traveler refresh their dashboard; confirm the DOCKGuide is accessible.
⚠️ Gap: All steps currently require direct Firestore writes. There is no admin UI for granting comped access. An "Issue Comp Access" tool is P1 for customer service operations.

Journey E — Run a Full Data Refresh Cycle

Trigger: Scheduled pipelines have failed, data is stale, or a major cruise line has published schedule updates. Goal: Refresh all cruise and port data end-to-end.
  1. Trigger Cruisemapper sync — Go to API Maintenance (/admin/maintenance) and click "Run Now" for Cruisemapper. Wait for the Cloud Function to complete.
  2. Monitor change detection — The detectCruiseRawChanges Cloud Function runs automatically after ingestion. Check Firestore cruiseChanges collection for any detected modifications.
  3. Review and apply changes — If significant itinerary changes are detected, trigger applyCruiseChanges. Travelers with affected itineraries will see the change alert modal on next login.
  4. Trigger Apify scrape — Run Apify on-demand for supplemental port data if needed.
  5. Refresh alerts — Trigger "Alerts Trigger Fetch" to pull the latest government advisories.
  6. Recalculate DockScores — If alerts changed, affected port DockScores are auto-invalidated. Trigger dockCalculateAdjusted for any ports that need a manual recalculation.
  7. Verify — Spot-check a few high-traffic ports in the traveler-facing dashboard to confirm data looks correct.
⚠️ Gap: Steps 2 and 3 require Firestore console access. There is no admin view showing the change detection queue or allowing review of detected changes before applying them. A "Pending Changes" review screen would be useful (P2).

Journey F — Investigate a Pipeline Failure

Trigger: Data is noticeably stale, a traveler reports missing weather or alerts, or a scheduled function failed silently. Goal: Diagnose the failure and restore the pipeline.
  1. Check Firebase Functions logs — Open Firebase Console → Functions → Logs. Filter by function name and time window to find error messages.
  2. Identify the failure type — Common causes: API key expiry (check API Keys page), Travefy rate limiting, Cruisemapper response change, network timeout.
  3. Fix the root cause — For key expiry: rotate in API Keys page. For Travefy issues: check travefyEcho admin function to verify platform connection. For schema changes: inspect raw data and update the parser.
  4. Trigger a manual run — Once the root cause is fixed, use API Maintenance to trigger the affected pipeline manually.
  5. Verify — Confirm data has updated (check a specific port or cruise record in Firestore).
⚠️ Gap: All pipeline health information currently lives in Firebase Console logs — there is no admin UI for monitoring pipeline status. A Pipeline Health Dashboard showing last run time, success/fail, and error summaries for each pipeline would significantly reduce the time to detect and diagnose failures (P1).

Journey G — Audit and Fix Content Gaps for a Region

Trigger: Preparing for a new cruise season, or a region's content quality review. Goal: Ensure all high-traffic ports in a region have complete, current guides.
  1. Open Content Health — Navigate to /admin/content-health; filter by region.
  2. Prioritize by port traffic — Cross-reference with port utilization data to identify which incomplete ports see the most sailings. (Currently requires manual cross-referencing — no integrated view.)
  3. Generate content in batch — For each incomplete port, use "Generate Port Content" section by section. Review each draft before moving to the next port.
  4. Fact-check existing content — For ports with existing content flagged as stale, run fact-check and apply corrections.
  5. Track progress — Re-run Content Health report to verify the region's completeness % has improved.
⚠️ Gap: There is no batch content generation — each port requires individual navigation. A "Generate for all incomplete ports in region X" bulk operation would dramatically speed up content work (P2). There is also no completeness % metric by region (P1).

Journey H — Manage a Traveler Order (Refund or Issue)

Trigger: A traveler contacts support requesting a refund, a duplicate charge, or reports their purchase is not showing up. Goal: Resolve the order issue.
  1. Find the traveler — Search by email in Firebase Auth to get the UID.
  2. Look up their orders — Query orders Firestore collection filtered by UID. Review order status, amount, Stripe session ID, and timestamp.
  3. Issue a refund — Use Stripe Dashboard to refund via the session ID from step 2.
  4. Update access — If the refund removes access, set users/{uid}.hasPurchasedCompass: false and remove the cruise from cruiseInstances.
  5. Confirm resolution — Verify the traveler's dashboard reflects the updated access state.
⚠️ Gap: Steps 1–4 all require direct Firestore or Stripe console access — there is no integrated order management UI. An Order Lookup page where admins can search by email, view order history, and trigger refunds via Stripe API is P1 for customer service.

Journey I — Deactivate or Reactivate an Agency

Trigger: An agency has stopped paying, is being offboarded, or a previously inactive agency is being re-activated. Goal: Update the agency's active status cleanly.
  1. Find the agency — Navigate to /admin/agencies and locate the agency by name or owner email.
  2. Open agency detail — Click "View →" to open /admin/agencies/:id.
  3. Toggle active status — Click "Deactivate Agency" or "Activate Agency". This updates agencies/{agencyId}.isActive in Firestore.
  4. Notify advisors — If deactivating, communicate to the agency host and advisors. (No automated notification is triggered by the status change.)
  5. Handle advisor access — Currently, deactivating an agency does not automatically suspend the agency's advisors. Each advisor's access must be managed separately via the agency roster.
⚠️ Gap: Deactivating an agency does not cascade to suspend affiliated advisors. A "Deactivate agency + suspend all agents" option would prevent overlooked access after an offboarding (P2). There is also no automated notification to the agency host (P2).

Journey J — Manually Fix a Travefy Connection

Trigger: An advisor used a different email address in Travefy than in DockBound, so auto-linking failed. Goal: Manually link the correct Travefy account to the advisor's DockBound UID.
  1. Confirm the advisor has authorized DockBound in Travefy — The advisor must have visited travefy.com/account/authorize/dockbound and approved access. If not, direct them there first.
  2. Get the advisor's Firebase UID — Find it in Firebase Console → Authentication by searching their DockBound email. Or ask the advisor to share it from their profile URL.
  3. Get the advisor's Travefy email — The email they use to log into Travefy (may be a different address).
  4. Run the link tool — Navigate to Agent Tools (/admin/agents); enter the UID and Travefy email; click "Link Travefy Account".
  5. Verify — Ask the advisor to attempt a Travefy sync from their dashboard and confirm trips appear.
✅ Built — The Link Travefy Account tool in Agent Tools is the only fully functional advisor management tool currently available in the admin portal.

5. Financial & Order Management

DockBound generates revenue from two sources: traveler DOCKGuide purchases (one-time Stripe payments) and advisor subscriptions (recurring Stripe billing). Currently, all financial data lives in the Stripe dashboard — there is no integrated financial view inside DockBound itself.

All items in this section are gaps. The Sales Revenue Lift Projection page (/sales/revenue-lift-projection) is a prospecting tool for modeling potential value for agency clients — it does not show actual platform revenue.

Non-keyword messages continue to route to traveler communication threads.

Backfill script (scripts/backfill-agency-nodes.cjs) run against dev and prod. Hierarchy lives exclusively in the Node system — no parentAgencyId or other hierarchy fields on the Agency model.
Built 60-Day Trial at Onboarding (Both Advisor Types — Different Mechanics) Both travefyadvisor and independentAdvisor sign-up paths provision a 60-day free trial. Travefy Advisor path: no Stripe payment required at signup — trial is held via a local trialEndsAt timestamp. Independent Advisor path: Stripe checkout with trial_period_days: 60 is required at onboarding; credit card is collected but billing starts at day 61. hasPaidAdvisorAccess() checks plan.status === 'trialing' and whether trialEndsAt is in the future.

Built in src/pages/agency/AdvisorDetailPage.tsx.
