3. Admin Journeys A–K

Journey A — Provision a New Agency Host

  1. Go to /admin/agencies → click "New Agency"
  2. Enter agency name, website, phone; click Save — creates agencies/{agencyId} doc
  3. Go to /admin/agents → "Promote to Agency Host" — sets users/{uid}.role = agencyhost
  4. Go to /admin/agencies/:agencyId → confirm host UID is linked
  5. Optionally: go to /admin/host-contracts and create a contract for the agency (commercial model, pricing, billing terms)
  6. Write audit log entry is automatic — check /admin/audit-log to confirm

Journey B — Onboard an Advisor to an Agency

  1. Advisor must already have a DockBound account (created via /auth)
  2. Go to /admin/agencies/:agencyId → "Add Advisor" (or instruct the host to use CSV import at /agency-hub/import)
  3. Confirm advisor appears in agency roster with status invited
  4. sendRosterInviteEmail fires automatically (Firestore trigger on roster doc creation)
  5. Advisor clicks invite link → linkAgentRoster CF fires → status changes to active
  6. Confirm in /admin/advisors/:uid that agencyId is set and role is correct

Journey C — Override an Advisor's Plan / Tier

  1. Go to /admin/advisors → find the advisor by email or name
  2. Click advisor row → opens /admin/advisors/:uid
  3. In the "Plan Override" card: set tier (25/100/300/750), slot cap, and/or subscription status override
  4. Click Save — writes planOverride to agents/{uid}; audit-logged automatically
  5. To remove override: clear the fields and save again

Journey D — Suspend or Restore an Advisor

  1. Go to /admin/advisors/:uid
  2. Click "Suspend" — sets agents/{uid}.suspended = true; advisor dashboard shows locked state
  3. To restore: click "Unsuspend" — clears the flag
  4. Both actions are audit-logged; check /admin/audit-log for the entry

Journey E — Grant Comp Access to a Traveler

  1. Go to /admin/orders
  2. Search by the traveler's email address
  3. Click "Grant Comp Access" — sets users/{uid}.hasPurchasedCompass = true and writes a comp order doc
  4. Traveler immediately sees full DockGuide on their dashboard; audit-logged

Journey F — Generate AI Port Content

  1. Go to /admin/content-health
  2. Find a port with missing or stale sections
  3. Click "Generate" for the section(s) you want to fill
  4. adminGeneratePortContent CF calls OpenAI (GPT-4o) and writes to locations/{portCode}/sections/{sectionKey}
  5. QA trigger (onSectionWriteQA) fires automatically — check QA Review tab to see pass/fail result
  6. If human_review_required: review in QA tab and approve or reject (adminSubmitQAReview)
  7. After bulk generation: run npm run dock:regen-baselines:dev to update DOCK baseline scores

Journey G — Review QA Flagged Content

  1. Go to /admin/content-health → "QA Review" tab
  2. Filter by status human_review_required
  3. For each flagged section: read the QA result (blocking rules, advisory flags, grounding score)
  4. Click "Approve" → adminSubmitQAReview CF sets qaStatus = approved on the section doc
  5. Click "Reject" → CF sets qaStatus = human_review_required with reviewer note; use the per-section Regenerate button on the rejected item to re-run generation for that section alone
  6. Never approve content with a blocking rule violation — fix the underlying issue first

Journey H — Review and Apply Cruise Changes

  1. Go to /admin/cruise-changes
  2. Review change log — rows show severity pill (green/yellow/red), change type (new/updated/deleted), and diff of mapped fields
  3. For high-severity changes (port swap, cancellation): review the diff carefully
  4. applyCruiseChanges CF applies accepted changes to the live cruises collection
  5. Affected advisor dashboards pick up the change on next load; change triggers detectCruiseRawChanges
  6. Travelers with the affected cruise see an itinerary change alert on their dashboard

Journey I — Create or Revoke a Partner API Key

  1. Go to /admin/api-keys
  2. Click "New Key" — enter label, owner, plan (sandbox / paid), and optional note
  3. Key is generated client-side via Web Crypto (dbk_{8hexId}_{secret} format); SHA-256 hash stored in api_keys/{8hexId}
  4. Copy the full key immediately — it is shown only once and cannot be recovered
  5. To revoke: click "Revoke" on the key row — sets active: false; CF rejects requests from that key
  6. To delete entirely: click "Delete" — removes the Firestore doc; all history is lost

Journey J — Resolve an Attention Item for an Agency Host

  1. Agency host sees item in /agency-hub Attention feed
  2. Host may escalate or be unable to resolve — admin enters /admin/advisors/:uid for the affected advisor
  3. Depending on item type: fix Travefy auth (Journey B/C), unsuspend advisor (Journey D), or override plan
  4. Admin marks item resolved via agency hub if they have agencyhost access — otherwise host must resolve
  5. Status transitions: new → viewed → actionPlanned → resolved; each appends to history[] audit trail
  6. Never select expiredWithoutAction as a status — this is system-derived only

Journey K — Handle a Data Subject Request (GDPR)

  1. Receive DSR from a data subject (email or support ticket) — 30-day SLA starts on receipt
  2. Go to /admin/dsr
  3. Enter the data subject's email address or Firebase UID in the lookup field
  4. Right of Access (Art. 15): click "Export data" — downloads a JSON file of all personal data held for that subject across Firestore collections. Send this file to the data subject within SLA.
  5. Right to Erasure (Art. 17): run "Dry run erasure" first — review the wouldDelete list to confirm scope. Then click "Erase account" and confirm the irreversible dialog. The CF deletes users, anonymises agents, deletes roster entries, communications, enrichments, guide overrides, and stored trips; anonymises the Stripe customer; deletes the Firebase Auth record; writes an erasure record to gdpr_erasure_log/{uid}.
  6. Confirm in /admin/audit-log that the erasure log entry was created (category: admin, summary: "GDPR account erasure for uid …")
  7. Reply to the data subject confirming completion. Audit log entry is the retention record — do not delete it.

6. Gap Analysis

Candor note: These are real gaps in the admin toolset. Priority ratings reflect operational risk, not development effort.

P1 — Blocking / High Operational Risk

GapImpactCurrent Workaround
No aggregate revenue dashboard (MRR/ARR) Cannot answer "how much is the platform making this month" without a Stripe export. No visibility into trial-to-paid conversion rate. Stripe Dashboard directly. Manual export.
Trial expiry not surfaced in admin UI Can't see at a glance which advisors have trials expiring soon. Risk of surprise churn with no proactive outreach. Firestore query on agents collection, filter by subscription.trialEndsAt.
No platform-level error alert center Cloud Function failures are silent in the admin portal. Only visible in Firebase Console logs, which require developer access. Firebase Console → Functions → Logs.

P2 — Significant Gaps

GapImpactNotes
Conflict detection queue not live The fieldTypes.conflictThreshold values are all null. rawFieldData observations are seeded but the detection queue (Phase 4 roadmap item) hasn't started. Field Data page shows observations but can't auto-flag conflicts. Manual "Pick Winner" via Field Data page works as a stopgap.
Advisor Stripe subscription not visible in admin UI Can't see subscription ID, current period end, or payment method from the Advisor Detail page. Must go to Stripe Dashboard with the advisor's email. Planned: surface Stripe subscription summary in Advisor Detail.
Host billing automation incomplete Host contracts and invoice generation are built, but there's no automated payment collection for host subscriptions — requires manual Stripe steps. stripeCreateHostSubscriptionSession CF exists but UI flow not fully wired.
Bulk port guide generation requires single-port UI Content Health page generates one port at a time. For batch operations on hundreds of ports, admin must use the CF directly or run scripts. Use adminGeneratePortContent CF directly via scripts for bulk runs.

P3 — Minor / Low Operational Risk

GapNotes
No advisor engagement score Activity per advisor visible in Usage page, but no computed score or ranking. Identifying "at risk of churning" advisors requires manual review.
Content freshness (age by port) not shown Content Health shows section presence, not when content was last updated. A port's content could be 6 months old with no visual indicator.
Node ID not surfaced in Advisor Detail The canonical hierarchy key (users/{uid}.nodeId) is not visible in admin UI — must use Firestore console to inspect or traverse the node tree.
Attention item resolution not available to admin role Attention items in Agency Hub can only be resolved by the agencyhost role user. Admins who don't have that role cannot resolve items on behalf of a host.
